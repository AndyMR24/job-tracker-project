# Development notes

Run tests with `python -m unittest discover -s tests`; the CV tests read generated PDFs with `pypdf`, so install the test extra first with `python -m pip install -e .[test]`. Tests that need `pdflatex` are skipped when LaTeX is unavailable. Runtime code uses the standard library plus `geonamescache` for offline city coordinates.

The test suite uses synthetic fixtures: `tests/support.py` provides a fictional profile and search configuration, and every module writes its data into a temporary directory, so no test reads a real profile, source CV or database, and no test needs credentials or network access. `tests/test_examples.py` keeps the shipped `data/*.example.json` files loadable. Personal files (`data/profile.json`, `data/search_config.json`, `MASTER_PROFILE.md`, `SOURCE_CV.pdf`, `*.sqlite3`) are untracked by design; only the example files are committed, so a fresh clone starts from placeholders.

The CLI reconfigures standard output and error to UTF-8 with replacement characters, so listings containing emoji or non-Latin titles survive being piped or redirected. It also closes its SQLite connection when a command finishes and exits quietly when a reader closes the pipe early.

`profile.py` validates editable factual data. `normalizer.py` gives incomplete listings a consistent shape without inventing fields. `evaluator.py` makes conservative, transparent rule-based assessments, including the small additive `preferred_languages` signal (structured requirement mentions outweigh qualification text, which outweighs prose, and it never excludes a job or outweighs core fit). `storage.py` is local SQLite state and audit logging. `cv.py` produces local LaTeX-generated PDF drafts from profile facts. The public sources live in `adzuna.py`, `nomado24.py`, `himalayas.py`, and `ba.py`; each maps public listings into the existing raw-job shape. `cli.py` coordinates the workflow and stops the whole run with a clear message if any single source fails. `search.py` remains isolated legacy DuckDuckGo code and is not an active automated source.

The dashboard stays thin: `discovery.py` holds the public-search orchestration (query ordering, per-source de-duplication, optional error tolerance) and the normalize/evaluate/store pipeline, and both `cli.py` and the dashboard call it, so search behavior is defined once. `dashboard.py` contains read-only projections (filtering, sorting, aggregates, audit and search history) over rows returned by `Store`; evaluator-excluded jobs and user-rejected jobs are hidden unless a filter asks for them. `webui.py` renders server-side HTML and escapes every dynamic value. `webapp.py` serves it with the standard library HTTP server: routes map onto `Store`, `discovery`, `cv.generate` and `dashboard`, generated PDFs are served from the recorded path, and dashboard-initiated searches run in one background thread with a JSON status endpoint.

Start it with `job-agent dashboard --port 8771` or `python -m job_agent.webapp --port 8771`. It binds to 127.0.0.1 by default and adds no dependency beyond the standard library. `tests/test_dashboard.py` covers the read models plus real HTTP requests against a temporary database and a stub source adapter, so dashboard tests never touch the network or the local database.

`maintenance.py` re-runs the current evaluator over already-stored jobs and backs `job-agent re-evaluate`: it rebuilds each `Job` from the stored payload, compares the fresh evaluation with the stored one, and asks `Store.replace_evaluation` to rewrite only differing rows, so listing facts, decisions, applications and audit history stay untouched.

Source field notes verified against live responses on 2026-09-23: a Himalayas search item publishes `locationRestrictions` (a list of country names, present on every sampled item and empty for worldwide roles) and `timezoneRestrictions` (UTC offsets). Those country names are the only structured geographic eligibility signal the source offers, and `location.resolve_eligibility` interprets them against `employment_eligibility.country_of_residence` from the profile, so an explicitly restricted remote job is excluded while worldwide, Europe and Germany listings keep the existing remote handling. The same Himalayas payload has no `remote`/`isRemote` field, so the adapter intentionally leaves the arrangement unknown, and it publishes `minSalary`/`maxSalary`/`companyName`, which the adapter only partly reads today. The Bundesagentur fuer Arbeit Jobsuche search item exposes the employer application link as `externeURL` (capital URL) for roughly half of the sampled listings, the detail payload does not repeat it, and the API publishes no canonical arbeitsagentur.de posting URL; the adapter preserves `externeURL` when present and leaves `source_url` unknown otherwise rather than constructing a link.

The MVP intentionally uses only exact URL/job-ID duplicate prevention and basic work-authorization flags. It stores no credentials (the Adzuna adapter reads its keys from the environment or a local `.env`), has no browser or application automation, and has no code path that transmits a profile, CV or local record to an external service.
